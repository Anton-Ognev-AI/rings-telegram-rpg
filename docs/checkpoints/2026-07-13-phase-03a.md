# Phase 3A Checkpoint — Telegram Service Contracts

**Status:** `approved` locally on 2026-07-13. Gate 3B may start. No remote project was linked, migrated, deployed, or connected to Telegram.

## Delivered

- Forward-only migration `202607130009_telegram_commands.sql` adds service-only Telegram identity bootstrap, fallback-day publication/advancement, current-window run start, owner-bound run view, explicit abandon, and leased outbox delivery.
- Identity bootstrap persists only the numeric Telegram identity link required by the game. It never accepts or stores username/display name and remains idempotent under 20 concurrent calls.
- `start_run_v2` derives the Kyiv cycle from an injected timestamp, permits starts only during the open interval, blocks a previous run during grace, expires it after grace, and atomically creates the initial `render_run_state` intent.
- Outbox workers use opaque lease UUIDs, `FOR UPDATE SKIP LOCKED`, bounded leases and ten attempts. Retryable, permanent, delivery-unknown, superseded, and sent outcomes are distinguished.
- Stale run-state intents are suppressed before leasing, an active lease serializes delivery for the same run, and a conflicting Telegram message ID is rejected. This prevents an older render from rolling the canonical card backward.
- `telegram_run_cards` stores only internal run/player IDs, Telegram message ID, and last rendered state version. Outbox payloads store neither Telegram identity, rendered text, username, callback token, nor secret.
- Eight new public RPCs are `security definer`, pin `pg_catalog, game, pg_temp`, and grant execution only to `service_role`; API roles retain no direct private-table access.
- Narrow TypeScript application wrappers serialize Telegram `bigint` values as decimal strings so JavaScript precision is not lost.
