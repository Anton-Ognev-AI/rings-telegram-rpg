# Phase 2 Checkpoint — Persistent Atomic Core

**Status:** `approved` locally on 2026-07-13. Phase 3 planning is the next active task. No remote project was linked, migrated, or deployed.

## Outcome

Phase 2 now provides a reproducible private Postgres core for the Telegram Academy game:

- normalized config, surrogate identity, player stats, immutable content, Kyiv daily cycles, XP ledger, runs/snapshots, prepared actions, immutable results, outbox, and privacy-safe analytics;
- deny-by-default private `game` schema with RLS and no direct API-role access;
- six service-only, versioned, `security definer` public RPCs with safe pinned search paths;
- one atomic choice transaction across run state, XP, stage result, processed cache, analytics, and outbox;
- deterministic retry behavior under stale callbacks, 100 duplicates, competing choices, lost responses, update-ID conflicts, zero-XP outcomes, and actor/context tampering;
- deletion orchestration with a non-PII tombstone in a logically separate local recovery database and idempotent replay into an isolated restored-primary test database;
- canonical migration checksums, public RPC database types, reconciliation, and one full verification command.

Gate details remain in [Phase 2A](./2026-07-13-phase-02a.md) and [Phase 2B](./2026-07-13-phase-02b.md).

## Controlled local deviations

- Docker Desktop runs the Supabase stack, but this terminal has no standalone `docker`/`podman` executable. Therefore `supabase test db` and `supabase gen types` cannot launch their helper containers. The same pgTAP SQL is executed by the pinned loopback-only Postgres driver, and the public-RPC TypeScript contract is generated from migration 008 and checked by Deno. No private table is exposed in that type surface.
- Recovery control uses a separate logical database `recovery_control` on the local Postgres instance rather than a second local container/port. The restore test targets a different disposable database, proving the tombstone remains outside the restored primary database. Production must provision recovery control as a separately operated store before testers are invited.
- `SHA256SUMS` lives beside migrations as planned; Supabase CLI logs a harmless “skipping migration” notice because the manifest is intentionally not an SQL migration.

## Rollback and operational boundary

- Local primary/recovery data is synthetic and disposable. Rollback before merge is the previous Gate 2B commit `835a00c`; after merge use new forward migrations rather than rewriting canonical files.
- Stop the LAN-visible local stack after work with `npx supabase stop --no-backup`.
- Phase 2 does not authorize remote migration, service-role secret provisioning, Telegram webhook registration, tester invitations, or deployment.
