# Phase 2A Checkpoint — Private Persistent Schema

**Status:** `approved` locally on 2026-07-13. Gate 2B may start. No remote project was linked or changed.

## Delivered

- Four ordered forward-only migrations create the private `game` boundary, pinned enums, immutable versioned config, kill switches, surrogate players/Telegram identity links, typed player stats, validated immutable content, Kyiv-local dungeon days, and a reviewed fallback slot.
- `anon`, `authenticated`, and `service_role` have no `USAGE` on `game` and no direct table access. RLS is enabled on every Phase 2A table; later service commands must enter only through explicit public RPCs.
- Local DB tools reject non-loopback URLs, use pinned `postgres@3.4.7`, run pgTAP directly against the local Supabase database, and compute ordered migration hashes.
- Content seeding reuses the locked Phase 1 validator and canonical SHA-256. The committed fallback hash is `9f136eb4d007c6c6b112aaece1f996906b8dad893318ebcc1e95d376b8e84851`.
- Config V1 hash is `e62656603ca981577373bcbbebcb78d29ad161431e1aa9adcfbb8c2392ff79ef`; daily XP cap remains 150.
- Dungeon-day constraints use consecutive 09:00 `Europe/Kyiv` boundaries, preserving 23/25-hour UTC cycles at DST transitions and the two-hour grace window.

## Controlled deviation and residual limits

- `supabase test db` could not launch its `pg_prove` wrapper because this verified Docker Desktop installation exposes the daemon to Supabase CLI but does not install a standalone `docker` executable in the current PATH. The local runner therefore executes the same pgTAP SQL through the pinned Postgres driver and rejects `not ok`, missing plans, and incomplete plans. Its parser has three unit tests.
- The local Supabase ports remain potentially LAN-accessible as recorded in Phase 0. Only synthetic identities are present, the owner confirmed a trusted network, and the stack must be stopped after the phase.
- No XP, run, action, outbox, Telegram handler, remote migration, or deployment is included yet.
