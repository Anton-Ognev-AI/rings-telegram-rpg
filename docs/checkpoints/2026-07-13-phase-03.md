# Phase 3 Checkpoint — Telegram Fallback-First Vertical Slice

**Status:** approved locally
**Scope:** Phase 3 Gates 3A–3C
**Environment:** synthetic identities, fake Telegram, loopback Postgres; no remote project, deploy,
webhook registration, real credentials, or external testers

## Delivered

- persisted `/start → expedition → stages 1–10 → summary` fallback run with restart-safe resume,
  opaque actor-bound callbacks, one canonical Telegram card, deterministic mechanics, and
  P01-informed Ukrainian rendering;
- service-only identity, start, run-view, day lifecycle, render-repair, deletion and outbox RPCs in
  checksum-pinned forward migrations 009–013;
- recovery-backed `begin → non-PII tombstone → finalize` identity deletion. A current attempt time
  is separate from the immutable tombstone time, and a failed/malformed read-after-error can never
  be interpreted as completed deletion;
- deletion/outbox fencing that blocks new gameplay and delivery, supersedes queued work, waits for
  a live lease, and finalizes only after no pending or leased delivery remains;
- a durable pre-send dispatch marker. If a worker crashes after arming a new send, lease expiry
  moves it to terminal `delivery_unknown` instead of blind resending; edits remain safely retryable;
- a 15-second delivery authorization with a transport timeout capped at 10 seconds and a drain
  margin before lease expiry;
- exact normal/DST open, close and grace boundaries, including abandoning yesterday's run during
  grace and immediately starting the current day;
- a self-contained `npm run verify:phase3` command that rejects remote DB overrides and linked
  Supabase projects, starts the local stack with isolated CLI state, suppresses local key output,
  runs every stateful group sequentially, and stops the stack in `finally`;
- a 6,000-callback synthetic capacity gate across 60 independent canonical runs. It requires
  effective throughput of at least 10 callbacks/s, p95 acknowledgement below 2 seconds, zero
  duplicate game effects, zero lost outcomes, bounded backlog, and a final empty queue.

## Controlled Limits and Accumulated Proposals

- The load gate is a closed-loop local capacity proof with fake Telegram, not a paced real Telegram
  soak. Real transport rate limits and staging cron remain later external gates.
- Ambiguous new sends deliberately stop at `delivery_unknown`. Before deployment, define an
  operator reconciliation action instead of adding automatic blind retry.
- Distinct cached duplicate updates currently create edit-only repair intents. The gate proves
  bounded processing, but 5,940 cached callbacks also caused 5,940 synthetic repairs; coalescing or
  throttling repairs by run/state should be considered before a public alpha.
- The recovery-control store is logically isolated in the local synthetic database. Production
  provisioning, restore rehearsal and retention policy remain separate staging work.
- No external core-loop validation was performed. The master plan still requires 5–10 testers and
  its UX metrics before Phase 4 and Parallel Track G, unless the owner explicitly approves a waiver
  or plan amendment.
