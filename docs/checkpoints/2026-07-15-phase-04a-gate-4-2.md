**Status:** implementation complete; `verification_hold`. Gate 4.2 remains `in_progress` until the

## Delivered

- `player_home_v1` is the strict server projection for tutorial state, pending decisions, exact
  stat forecasts, personal best and the contribution-based starter build. TypeScript validates and
  renders this projection; it does not recompute persistent combat values.
- The focused progression router gives pending item/ring/training decisions priority, starts runs
  only through server-derived `start_run_v3`, and routes `/start`, expedition, resume, hero,
  Academy, help and `pa_` callbacks without restoring client-injected builds in production.
- Profile actions are opaque and bound to actor, profile version and the existing canonical Telegram
  message. Stateful cards edit that message through the outbox; direct hero/Academy/help views are
  compact read-only projections.
- Terminal tutorial cards now expose the first stat choice, no-inventory item decision, four-way
  blue ring choice and ring mastery. The item can only replace its slot or be discarded.
- `request_run_render_v2` derives idempotency from run/state under a run lock. Concurrent repair
  requests coalesce, while a later stale/cached callback can enqueue a new edit without creating a
  second canonical card.
- A blocked expedition restores its unresolved canonical decision instead of returning silently.
  Rejected profile actions show one generic recovery card without leaking token or state details.
- Phase 3 E2E helpers retain legacy build injection only for explicit synthetic fixtures and use the
  v2 progression RPCs for the production-shaped path.

## Council Review

The five-role review returned `APPROVE_WITH_VERIFICATION_HOLD` after three corrections:

1. **Player experience:** expedition rejection during a pending reward/training decision was silent.
   The router now restores the exact canonical decision and gives a visible fallback for other start
   rejections.
2. **Security and UX:** rejected or malformed profile actions only acknowledged the callback. They
   now show one generic recovery path without revealing whether the token, profile or message was
   stale.
3. **Reliability:** Phase 3 delivery-fault fixtures still controlled v1 render idempotency with a
   client key. The obsolete input was removed; v2 server-side coalescing remains the only production
   contract.

Architecture remains focused: the handler shrank while progression policy moved to one router;
database projections remain authoritative; mutation actions remain message-bound; and no inventory,
future partner shell or remote surface was added.

## Residual Product Risks

- The current fallback dungeon still has the monotony observed in P01. Gate 4.2 makes progression
  visible but does not add new teachers, lessons or content variety; that remains a later content
  phase and Telegram validation question.
- Stat-price arithmetic is intentionally pinned twice inside the active v1 migration (forecast and
  mutation). A future progression version should centralize it in a versioned SQL helper before
  changing coefficients.
- Direct hero/Academy/help cards are read-only by design; mastery remains available only on the bound
  canonical terminal card until a later canonical profile-card design is approved.
